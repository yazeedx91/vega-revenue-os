# AID-001: Multi-Agent Topology: Mission Orchestrator + Planner + Specialist Agents

- **Decision ID:** AID-001
- **Status:** Proposed
- **Date:** 2026-08-08
- **Owner:** Chief AI Architect / Architecture Review Board

## Decision

Adopt a **Mission Orchestrator → Planner → Specialist Agents → Policy & Authorization Layer → Tool Gateway → External Systems** topology as the recommended AI architecture.

## Context

The AI-Native Autonomous Revenue Employee must perform diverse tasks: research, ICP evaluation, lead qualification, outreach, conversation handling, meeting scheduling, CRM updates, follow-up, and learning. A single general-purpose agent lacks cohesion, observability, and safety. A pure swarm or fully emergent multi-agent design introduces unacceptable operational and audit risk. A planner+executor split alone does not capture domain specialization.

## Recommended Topology

```
Mission Orchestrator
        ↓
    Planner
        ↓
Specialist Agents
        ↓
Policy & Authorization Layer
        ↓
    Tool Gateway
        ↓
External Systems
```

## Responsibilities of Each Component

### Mission Orchestrator

- Coordinates the lifecycle of a revenue mission.
- Delegates planning to the Planner.
- Assigns tasks to Specialist Agents.
- Handles events from agents, tools, and external systems.
- Manages human approval gates and mission state.
- Tracks mission progress against objectives.
- Does NOT contain specialist domain logic.

### Planner

- Creates the initial mission plan.
- Revises plans based on observations, outcomes, and failures.
- Decomposes objectives into specialist tasks.
- Defines approval gates and fallback branches.
- Does NOT execute external actions or bypass policy.

### Specialist Agents

Narrow, capability-bounded agents that perform specific tasks:

- Research Agent
- ICP Qualification Agent
- Lead Qualification Agent
- Buying Signal Agent
- Outreach Strategist Agent
- Outreach Writer Agent
- Conversation Agent
- Meeting Agent
- CRM Agent
- Follow-up/Nurture Agent
- Compliance/Safety Monitor Agent

Each specialist:

- Has a defined role, capabilities, and tool set.
- Queries Policy & Authorization before external actions.
- Uses Tool Gateway for all external interactions.
- Produces structured outcomes and evidence.
- Can be evaluated, versioned, and scaled independently.

### Policy & Authorization Layer

- Evaluates every proposed action against policy, autonomy level, risk, and tenant context.
- Returns ALLOW / REQUIRE_APPROVAL / DENY.
- Cannot be bypassed by any agent or orchestrator.
- Manages capabilities, approvals, and emergency stop.

### Tool Gateway

- Executes authorized tool calls.
- Validates inputs and outputs.
- Enforces tenant isolation.
- Records audit and telemetry.
- Handles retries, fallback, and failure.

## Agent Boundaries

- Each agent has a single primary responsibility.
- Agents do not share mutable state.
- Agents communicate through the orchestrator or events, not unbounded peer-to-peer conversations.
- Agents cannot self-elevate capabilities.
- Agents cannot directly call external systems.

## Authority Boundaries

| Component | Can Decide | Cannot Decide |
|---|---|---|
| Mission Orchestrator | Mission-level sequencing, delegation, pause/resume | Policy, capability assignment, external action authorization |
| Planner | What tasks should be done, in what order | Whether actions are allowed, execution of external actions |
| Specialist Agent | How to perform its scoped task | Whether policies permit an action, direct external execution |
| Policy & Authorization | ALLOW / REQUIRE_APPROVAL / DENY | Mission objectives or business strategy |
| Tool Gateway | Execute validated, authorized tool calls | Authorize actions |

## Communication Model

- Orchestrator ↔ Planner: command/response for plan creation/update.
- Orchestrator → Specialist Agent: task commands via event bus or in-process ports.
- Specialist Agent → Policy & Authorization: synchronous policy query.
- Specialist Agent → Tool Gateway: authorized tool execution request.
- Specialist Agent → Memory/Knowledge/LLM: read operations.
- All significant outcomes published as domain events.
- All external actions routed through Tool Gateway.

## Failure Handling

- Orchestrator detects missed task deadlines and failed executions.
- Planner re-plans on failure or unexpected outcome.
- Specialist failures are isolated; mission continues if possible.
- Policy denials halt action and trigger escalation/audit.
- Tool Gateway failures retry or fall back per policy.
- Persistent failures move mission to Blocked or Failed state with audit.

## Security Implications

- Centralized policy enforcement prevents agents from bypassing controls.
- Tool Gateway is the only path to external systems, enabling uniform audit and validation.
- Specialist isolation limits blast radius of a compromised or misbehaving agent.
- Versioned agents allow rollback of bad behavior.
- Tenant isolation maintained across all layers.

## Scaling Implications

- Mission Orchestrator can be replicated statelessly; mission state persisted externally.
- Planner is a compute-heavy but stateless component; can be scaled independently.
- Specialist agents can be scaled as worker pools per capability (e.g., more Conversation Agents).
- Tool Gateway scaled per external provider load.
- Policy & Authorization must be low-latency and highly available; caching used for stable policy rules.

## Cost Implications

- Specialist agents allow cheaper models for narrow tasks.
- Planner can use a stronger model only for complex re-planning.
- Orchestrator is mostly state management and routing, low model cost.
- Tool Gateway can batch and rate-limit external calls.
- Token budgets applied per task and per mission.

## Observability Implications

- Clear ownership per component simplifies tracing.
- Each task is traceable from mission → orchestrator → planner → specialist → policy → tool → outcome.
- Component-level metrics: latency, success rate, token/cost per component.
- Failure attribution is straightforward.

## Alternatives Considered

### 1. Single General-Purpose Agent

- **Pros**: Simplest architecture, one context window, one codebase.
- **Cons**: Unbounded authority, poor observability, hard to evaluate, high blast radius, cannot scale specialists independently, violates cohesion and separation of concerns.
- **Verdict**: Rejected. Does not meet authority, observability, evaluation, or safety requirements.

### 2. Planner + Executors

- **Pros**: Clean planning/execution split.
- **Cons**: Executors tend to become generic and lose domain specialization; does not naturally express revenue-domain specialists (research, qualification, outreach, conversation, CRM).
- **Verdict**: Partially valid. Absorbed into recommended topology: the Planner remains, but execution is performed by domain specialists rather than generic executors.

### 3. Hybrid / Swarm Architecture

- **Pros**: Flexible, can handle emergent coordination.
- **Cons**: Hard to debug, non-deterministic, audit and policy enforcement difficult, risk of unbounded agent-to-agent communication.
- **Verdict**: Rejected for initial architecture. May be revisited experimentally under strict governance if a specific task proves unsuitable for orchestrator-led delegation.

## Conditions Under Which the Topology Should Change

- A new mission type requires fundamentally different coordination (e.g., real-time collaborative planning).
- The number of specialists grows beyond manageable size and a hierarchical supervision layer becomes necessary.
- Latency requirements demand in-process planning and execution for a subset of tasks.
- A task proves better suited to emergent coordination after controlled evaluation.
- Cost analysis shows orchestrator overhead dominates and simplification is justified.

## Migration Path

- Introduce new specialists without changing orchestrator or policy contracts.
- Move Planner in-process if needed, preserving its interface.
- Extract Mission Orchestrator to a standalone service when mission volume requires it.
- Add hierarchical supervision only after proving necessity.
- Maintain backward-compatible events during any topology evolution.
