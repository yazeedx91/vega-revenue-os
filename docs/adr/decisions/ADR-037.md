# ADR-037: Dynamics 365 CRM Adapter

- **ADR ID:** ADR-037
- **Status:** Proposed
- **Group:** Integrations
- **Date:** 2026-08-08
- **Decision Owners:** Architecture Board, CTO

## Context

The AI-Native Autonomous Revenue Employee requires clear integrations direction so that implementation, operations, and future evolution remain coherent. This ADR captures the relevant drivers, alternatives, and consequences for the dynamics 365 crm adapter concern.

## Problem

Multiple integrations options exist for dynamics 365 crm adapter. Without a documented decision, individual teams may choose inconsistent technologies or patterns, creating integration debt, security gaps, and operational sprawl.

## Requirements

- Normalize CRM objects
- support bi-directional sync
- handle rate limits

## Decision

Build a Dynamics 365 Dataverse and Web API adapter behind the normalized domain ports for Company, Contact, Lead, Opportunity, Activity, and Meeting.

## Alternatives

1. **Call Dynamics 365 entities directly from core logic**
2. **Build a full ETL batch pipeline**

## Rationale

An adapter hides Dynamics specifics, maps to normalized domain objects, and lets the AI and business logic remain provider-agnostic.

## Consequences

This decision aligns the integrations domain with the overall architecture. It enables consistency, reduces cross-cutting risk, and leaves room to revisit alternatives when validation data is available.

## Risks

- Mapping drift
- API limits
- authentication complexity

## Mitigations

- Contract tests
- rate limiting
- token refresh
- versioned mappings

## Security Impact

Provider adapters normalize external systems behind domain ports; credentials and tokens are stored in a secrets manager.

## Performance Impact

Caching, idempotency keys, and rate-limiting adapters protect downstream APIs from burst traffic.

## Scalability Impact

New CRM/ERP/email/calendar providers are added as additional adapters, not core changes.

## Cost Impact

Standardized adapters avoid bespoke integrations and enable reuse across tenants.

## Operational Impact

Adapter health and retry metrics are observable; failures are contained within the integration bounded context.

## AI Impact

The intelligence layer receives normalized domain objects, so prompts and planning logic remain provider-agnostic.

## Reversibility

High. The decision can be revisited when validation criteria or operational constraints change; alternatives are documented and can be re-evaluated.
