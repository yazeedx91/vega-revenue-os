# ADR-104: Outreach Execution Kernel Package Boundary

- **ADR ID:** ADR-104
- **Status:** Proposed
- **Group:** AI / Outreach
- **Date:** 2026-08-12
- **Decision Owners:** Architecture Review Board, CTO

## Context

Phase 11 produces qualified leads with evidence and explainable scoring. Phase 12 must execute controlled outreach without duplicating the intelligence engine, mission orchestrator, or generic AI runtime. We need a dedicated bounded context for outreach-specific business logic.

## Decision

1. Create a new `packages/outreach` package that owns:
   - Outreach domain aggregates/events/value objects (co-located under `packages/domain/src/outreach`).
   - Outreach planning, personalization, and execution services.
   - Provider ports and stub adapters for email, LinkedIn, and calendar channels.
   - Outreach-specific agent executor and registry for Mission Orchestrator integration.
2. `packages/outreach` depends on `packages/domain`, `packages/shared`, `packages/infrastructure`, `packages/ai-runtime`, and `packages/intelligence` (read-only for lead/evidence lookup).
3. `packages/mission-orchestrator` may depend on `packages/outreach` to inject the outreach agent executor/registry.
4. No outreach business logic is placed in `packages/ai-runtime`, `packages/intelligence`, or `packages/mission-orchestrator`.

## Alternatives

1. Put outreach inside `packages/intelligence`. Rejected: intelligence is research/qualification; outreach has different lifecycle, approval, and scheduling concerns.
2. Put outreach inside `packages/mission-orchestrator`. Rejected: the orchestrator should remain a generic mission executor, not a business-domain owner.
3. Create a top-level `apps/outreach-worker`. Rejected: a package is needed for shared domain/services before any worker app.

## Rationale

A dedicated outreach bounded context keeps the domain, application, and provider coordination concerns isolated while reusing existing infrastructure, AI runtime, and mission orchestration boundaries.

## Consequences

- Outreach can be developed, tested, and deployed independently of intelligence and orchestration.
- Mission orchestrator integration is achieved through well-defined agent contracts.
- A new package adds maintenance overhead, but the boundary is clear.

## Risks

- `packages/outreach` may grow; future decomposition into separate worker apps is still possible behind the existing ports.

## Security Impact

No direct security impact; tenant isolation is enforced at repository and service boundaries.

## Performance Impact

Minimal; package boundary is compile-time only.

## Scalability Impact

Positive; the outreach engine can be scaled independently as a worker pool.

## Cost Impact

None in Phase 12 (all providers are stubs).

## Operational Impact

Operations gain a clear package and port surface for monitoring outreach-specific behavior.

## AI Impact

Outreach personalization uses the existing AI runtime rather than introducing another LLM abstraction.

## Reversibility

Medium. The package can be split or merged as long as the domain and port contracts remain stable.
