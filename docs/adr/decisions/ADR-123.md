# ADR-123: Approval Boundary for First Outbound Email

- **ADR ID:** ADR-123
- **Status:** Proposed
- **Group:** Mission Orchestration / Outreach / Human-in-the-Loop
- **Date:** 2026-08-13
- **Decision Owners:** Architecture Review Board, CTO

## Context

Phase 10 introduced the `Approval` aggregate and `ApprovalApplicationService` for human-in-the-loop decisions. Phase 12 reused this boundary for outbound sends. Phase 14 introduces real email, so the approval boundary must be explicit and safe.

## Decision

1. **Every first outbound email to a new prospect/sequence requires human approval.**
2. After the first approved send, subsequent sequence steps may execute autonomously only when all of the following remain satisfied:
   - Tenant policy allows autonomous email sends.
   - Sequence/campaign policy allows autonomous execution.
   - Recipient is not suppressed.
   - Recipient has not opted out.
   - Autonomy level permits it.
   - Confidence/risk thresholds are satisfied.
   - Budget remains available.
   - Rate limits are not exceeded.
   - Content passes validation.
   - No other configured approval condition is triggered.
3. A new human approval is required whenever the action materially changes risk, target, channel, policy, or configured approval conditions.
4. The existing `ApprovalApplicationService` and `Approval` aggregate remain the single approval authority; no second email-specific approval system is created.

## Alternatives

1. **Approve the entire campaign once.** Rejected: too coarse; a single campaign-level approval does not review the actual message content per recipient.
2. **Require approval for every send.** Rejected: removes autonomy value after the first touchpoint is validated.
3. **Allow fully autonomous first sends at high autonomy levels.** Rejected: real external side effects to unknown recipients require human review before the first send.

## Rationale

First-send approval is the smallest human-in-the-loop boundary that prevents unvetted messages from reaching real prospects while allowing the system to autonomously continue a validated sequence. Reusing the existing approval service preserves architectural consistency.

## Consequences

- `OutreachExecutionService` must surface first-send tasks as `AWAITING_APPROVAL` before provider submission.
- `OutreachSequenceWorkflow` must wait for the `outreachApprovalGranted` signal.
- Approval records must reference the exact execution, sequence, and recipient.
- Autonomous continuation logic must be tested thoroughly.
