# ADR-129: Controlled Communication Enablement Mode (`ALLOWLIST_ONLY`)

- **ADR ID:** ADR-129
- **Status:** Accepted
- **Group:** Outreach / Safety / Go-Live
- **Date:** 2026-08-17
- **Decision Owners:** Architecture Review Board, CTO

## Context

Phase 14 Milestone 5 built the complete pre-send safety boundary (`SendSafetyGate`), including allowlist, suppression, independent approval re-verification, rate limiting, budget, idempotency, and content checks. Milestone 7 must enable real Microsoft Graph email only in a deliberately restricted mode so that first production use cannot accidentally become unrestricted mass outreach.

## Decision

1. The first real-email mode is explicitly named `ALLOWLIST_ONLY`. It is a deployment-time mode label, not a new policy engine.
2. `ALLOWLIST_ONLY` mode means:
   - Every recipient must be present in the tenant-scoped `IRecipientAllowlistRepository`.
   - First-send approval remains mandatory (`ADR-123`).
   - Suppression, rate limits, budget, and idempotency remain enforced.
   - The existing `SendSafetyGate` logic is unchanged; it already implements all of these checks.
3. The mode is asserted at composition-root startup: the process logs its active mode and refuses to start the outbound worker variant if the required allowlist repository is not wired or if `OUTREACH_LIVE_EMAIL_ENABLED` cannot be read from configuration.
4. `OUTREACH_LIVE_EMAIL_ENABLED` (default `false`) remains the provider-level kill switch inside `GraphEmailProvider` (`ADR-117`/Milestone 4). The mode label is orthogonal; both must be `true`/`ALLOWLIST_ONLY` for a real send to occur.
5. No other mode (e.g. `BROAD_OUTREACH`, `DOMAIN_ALLOWLIST`) is implemented in Phase 14.

## Alternatives

1. **Implement the mode as a new, separate policy engine in `SendSafetyGate`.** Rejected: duplicates the already-correct allowlist/suppression/approval/rate-limit logic and creates two places where a send can be denied.
2. **Allow first real sends without approval by setting `ALLOWLIST_ONLY`.** Rejected: violates `ADR-123` and the explicit requirement that first-send approval remain mandatory.
3. **Add a mode that enables sends to entire verified domains without explicit addresses.** Rejected: broader than `ALLOWLIST_ONLY`; deferred until a future ARB decision.

## Rationale

A named mode label plus startup assertions is the smallest control that prevents accidental configuration drift while reusing the proven Milestone 5 policy boundary. Keeping the kill switch inside the provider ensures that even a misconfigured composition root cannot bypass the `false`-by-default flag.

## Consequences

- `apps/temporal-worker` and any `apps/api` composition root that sends must declare the active mode.
- New automated tests assert that mode mismatch or missing allowlist wiring prevents the controlled variant from starting.
- Removing the `ALLOWLIST_ONLY` restriction or adding broader modes requires a new ARB decision.

## Security Impact

Positive: explicitly limits blast radius of a misconfigured deployment to pre-approved addresses.
