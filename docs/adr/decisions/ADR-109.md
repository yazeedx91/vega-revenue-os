# ADR-109: Scheduling and Sequencing Boundary with Temporal

- **ADR ID:** ADR-109
- **Status:** Proposed
- **Group:** AI / Outreach
- **Date:** 2026-08-12
- **Decision Owners:** Architecture Review Board, CTO

## Context

Outreach sequences require delayed steps, business-hour constraints, cancellation, pause/resume, retries, timeouts, and response waiting. Temporal is the workflow engine (ADR-018). We must avoid placing outreach business lifecycle state inside Temporal.

## Decision

1. `OutreachSequence` aggregate (in `packages/domain`) owns business state:
   - current step index
   - step statuses
   - `nextDueAt`
   - pause/resume timestamps
   - cancellation status
2. Temporal workflow (`outreach-sequence-workflow.ts`) owns scheduling, timers, and signals:
   - Sleeps until `nextDueAt`.
   - Waits for `responseReceived`, `pause`, `resume`, `cancel` signals.
   - Calls activities that mutate the aggregate through application services.
3. `ISequenceSchedulePolicy` computes `nextDueAt` from current time, delay, and business-hours policy. Implementation is in `packages/outreach`; Temporal uses the result.
4. Workflow queries the aggregate state via repository in activities before deciding the next action; it does not maintain parallel state in workflow variables.

## Alternatives

1. Store step progression only in Temporal workflow state. Rejected: violates DDD boundary; replay and recovery become opaque.
2. Use a cron/scheduler service instead of Temporal. Rejected: ADR-018 already selected Temporal for durability and observability.

## Rationale

Keeping business state in the aggregate makes the system testable, event-sourced, and resilient to workflow restarts, while Temporal handles the durable scheduling and signal orchestration.

## Consequences

- Sequences can be recovered from repository state alone.
- Temporal workflows are thin and deterministic.
- Business-hour logic is unit-testable outside Temporal.

## Risks

- Clock skew between Temporal workers and schedule policy could cause minor timing inconsistencies. Mitigated by recomputing `nextDueAt` on resume/restart.

## Security Impact

No direct security impact; tenant isolation enforced by aggregate repositories.

## Performance Impact

Minimal; scheduling computations are cheap compared to provider calls.

## Scalability Impact

Positive; Temporal workers can scale horizontally while sequences are sharded by tenant/recipient.

## Cost Impact

None beyond existing Temporal usage.

## Operational Impact

Operators can inspect sequence state in the repository without reading Temporal history.

## AI Impact

None.

## Reversibility

Medium. Changing the workflow boundary requires updating activities but does not affect aggregate invariants.
