# ADR-130: Local Integration-Test Infrastructure Boundary

- **ADR ID:** ADR-130
- **Status:** Accepted
- **Group:** Testing / Infrastructure / Phase 14.7c
- **Date:** 2026-08-17
- **Decision Owners:** Architecture Review Board, CTO, QA Engineering

## Context

Most of Phase 14 has been validated with deterministic in-memory doubles and, for persistence, with `FakePgPool` (monitored query text and parameters but not a real PostgreSQL wire protocol). The milestone spec requires validating the communication lifecycle against real PostgreSQL, Redis, and Temporal semantics without touching production Azure resources, production databases, or real customer data.

## Decision

1. Provide a reproducible local integration-test environment via `infra/docker-compose.integration.yml` containing PostgreSQL, Redis, and the Temporal development server image.
2. The environment is test-only. It must be documented as explicitly not being the production deployment architecture and must not automatically become one.
3. Integration tests live in `*.integration.spec.ts` files and run under a separate Jest project (`jest.integration.config.js`). They do not run as part of the default deterministic unit-test command.
4. Required harness components:
   - service readiness check (`scripts/integration/wait-for-services.ts`)
   - migration runner (`scripts/integration/run-migrations.ts`)
   - optional deterministic seed/cleanup helpers
   - health checks before tests start
5. Tests must fail clearly when dependencies are unavailable. They must clean up deterministically after themselves and use isolated test tenants.
6. Real Microsoft Graph outbound sends and real inbound webhooks are **not** part of this environment; they remain deferred to a separately-authorized go-live runbook. All email-provider and Graph-ingress adapters used in the integration suite are deterministic doubles or stub payloads.
7. Validation results are classified in the 7c completion report as PASS, FAIL, BLOCKED, or ENVIRONMENTAL; no real-infrastructure requirement is marked PASS based solely on mocks.

## Alternatives

1. **Re-use the existing `FakePgPool` and in-memory doubles for all 7c validation.** Rejected: the milestone explicitly requires real PostgreSQL/Redis/Temporal validation; mocks do not exercise wire semantics, RLS, transaction isolation, or Temporal replay.
2. **Spin up cloud-managed PostgreSQL/Redis/Temporal for tests.** Rejected: creates production-like credentials, cost, and blast radius before the lifecycle itself is proven locally; violates the "smallest environment" requirement.
3. **Run real Temporal server directly on the developer machine without Docker.** Rejected: harder to make reproducible across machines and CI; Docker Compose provides a clean reset and isolation.

## Rationale

A Docker Compose-based local stack is the smallest environment that exercises real wire semantics for all three dependencies, remains reproducible in CI, and can be destroyed and recreated deterministically. Keeping it separate from the production architecture document prevents accidental operational reuse.

## Consequences

- CI must support Docker Compose or integration tests will be BLOCKED.
- Integration test runtime is expected to be slower than unit tests; they run only on demand or in a dedicated CI job.
- The 7c completion report must clearly separate deterministic unit-test results from real-infrastructure results.

## Security Impact

The environment must never contain real tenant credentials, customer data, or production cloud keys. All secrets in the integration stack are fixture values.
