# ADR-039: Meeting Provider Adapter

- **ADR ID:** ADR-039
- **Status:** Proposed
- **Group:** Integrations
- **Date:** 2026-08-08
- **Decision Owners:** Architecture Board, CTO

## Context

The AI-Native Autonomous Revenue Employee requires clear integrations direction so that implementation, operations, and future evolution remain coherent. This ADR captures the relevant drivers, alternatives, and consequences for the meeting provider adapter concern.

## Problem

Multiple integrations options exist for meeting provider adapter. Without a documented decision, individual teams may choose inconsistent technologies or patterns, creating integration debt, security gaps, and operational sprawl.

## Requirements

- Schedule and join meetings
- support multiple providers
- keep core portable

## Decision

Use the Zoom API as the initial meeting provider and wrap it behind a provider-agnostic adapter for Teams, Meet, and others.

## Alternatives

1. **No video meeting integration**
2. **Build a custom meeting stack**

## Rationale

Zoom is widely adopted; an adapter pattern allows adding other providers without touching core scheduling logic.

## Consequences

This decision aligns the integrations domain with the overall architecture. It enables consistency, reduces cross-cutting risk, and leaves room to revisit alternatives when validation data is available.

## Risks

- API changes
- multiple provider behaviors

## Mitigations

- Common interface
- fallback to manual link
- contract tests

## Security Impact

Provider adapters normalize external systems behind domain ports; credentials and tokens are stored in a secrets manager.

## Performance Impact

Caching, idempotency keys, and rate-limiting adapters protect downstream APIs from burst traffic.

## Scalability Impact

New CRM/ERP/email/calendar providers are added as additional adapters, not core changes.

## Cost Impact

Standardized adapters avoid bespoke integrations and enable reuse across tenants.

## Operational Impact

Adapter health and retry metrics are observable; failures are contained within the integration bounded context.

## AI Impact

The intelligence layer receives normalized domain objects, so prompts and planning logic remain provider-agnostic.

## Reversibility

High. The decision can be revisited when validation criteria or operational constraints change; alternatives are documented and can be re-evaluated.
