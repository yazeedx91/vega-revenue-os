# ADR-112: Reply Ingress Port and Stub Strategy

- **ADR ID:** ADR-112
- **Status:** Proposed
- **Group:** Conversation / Integration
- **Date:** 2026-08-12
- **Decision Owners:** Architecture Review Board, CTO

## Context

Inbound replies will eventually arrive from email providers, LinkedIn, and possibly SMS. Phase 13 must define the ingress abstraction without committing to a specific external channel.

## Decision

1. Define `IReplyIngress` port with a channel-agnostic `ReplyIngressEvent` contract.
2. Provide `StubReplyIngress` for tests and deterministic simulation; it enqueues and dequeues events in-process.
3. Defer real email/IMAP/Graph webhooks, LinkedIn messaging APIs, and SMS adapters to a later phase.
4. Ingress adapters are responsible only for normalization; deduplication, PII scrubbing, and tenant routing happen in the application service.

## Alternatives

1. Build a real email webhook now. Rejected: requires credentials, security review, and operational infrastructure before the domain model is validated.
2. Model each channel with a separate interface. Rejected: premature; a single normalized event plus a channel field covers current needs.

## Rationale

A stable port plus a deterministic stub lets the team validate conversation logic end-to-end while keeping external integration scope controlled.

## Consequences

- No real external communication in Phase 13.
- Future webhook adapters must map provider payloads to `ReplyIngressEvent` and verify signatures.
