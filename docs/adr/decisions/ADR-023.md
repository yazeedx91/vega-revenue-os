# ADR-023: LLM Provider Abstraction

- **ADR ID:** ADR-023
- **Status:** Proposed
- **Group:** AI
- **Date:** 2026-08-08
- **Decision Owners:** Architecture Board, CTO

## Context

The AI-Native Autonomous Revenue Employee requires clear ai direction so that implementation, operations, and future evolution remain coherent. This ADR captures the relevant drivers, alternatives, and consequences for the llm provider abstraction concern.

## Problem

Multiple ai options exist for llm provider abstraction. Without a documented decision, individual teams may choose inconsistent technologies or patterns, creating integration debt, security gaps, and operational sprawl.

## Requirements

- Support multiple LLM providers
- enable per-tenant keys
- allow model swapping

## Decision

Build a multi-provider abstraction with OpenAI and Anthropic as primary providers, routing by capability, cost, and latency.

## Alternatives

1. **Single LLM provider lock-in**
2. **Self-hosted open-weight models**

## Rationale

A provider abstraction improves resilience, gives negotiation leverage, and supports per-tenant provider keys while avoiding early lock-in.

## Consequences

This decision aligns the ai domain with the overall architecture. It enables consistency, reduces cross-cutting risk, and leaves room to revisit alternatives when validation data is available.

## Risks

- API divergence
- testing matrix
- credential management

## Mitigations

- Adapter tests
- fallback chains
- standardized request/response envelope

## Security Impact

Provider keys, prompt data, and outputs are isolated per tenant; all high-impact actions require explicit approval.

## Performance Impact

Model routing and caching reduce both latency and cost by selecting the smallest capable model for the task.

## Scalability Impact

A multi-provider abstraction and tool registry let us add models and capabilities without core rewrites.

## Cost Impact

Usage is metered per tenant; cheaper models handle routine tasks and expensive models are reserved for complex reasoning.

## Operational Impact

Prompt versioning, model health checks, and fallback chains make AI services observable and maintainable.

## AI Impact

Structured output, confidence scoring, and citations are first-class concerns, directly improving agent reliability.

## Reversibility

High. The decision can be revisited when validation criteria or operational constraints change; alternatives are documented and can be re-evaluated.
