# ADR-060: API Rate Limiting and Abuse Prevention

- **ADR ID:** ADR-060
- **Status:** Accepted
- **Group:** Security
- **Date:** 2026-08-08
- **Decision Owners:** Architecture Board, CTO

## Context

The AI-Native Autonomous Revenue Employee requires clear security direction so that implementation, operations, and future evolution remain coherent. This ADR captures the relevant drivers, alternatives, and consequences for the api rate limiting and abuse prevention concern.

## Problem

Multiple security options exist for api rate limiting and abuse prevention. Without a documented decision, individual teams may choose inconsistent technologies or patterns, creating integration debt, security gaps, and operational sprawl.

## Requirements

- Protect APIs
- prevent abuse
- tenant-aware limits

## Decision

Apply rate limits per tenant, user, and endpoint using Redis with graduated responses and CAPTCHA for abuse.

## Alternatives

1. **No rate limiting**
2. **Hard caps only**

## Rationale

Graduated rate limits protect availability, prevent abuse, and allow legitimate spikes.

## Consequences

This decision aligns the security domain with the overall architecture. It enables consistency, reduces cross-cutting risk, and leaves room to revisit alternatives when validation data is available.

## Risks

- False positives
- bypass

## Mitigations

- Tunable limits
- allowlisting
- abuse alerting

## Security Impact

This decision is itself a security control; it sets the boundary for identity, authorization, encryption, and audit.

## Performance Impact

Fine-grained authorization is enforced closest to the data to avoid repeated policy checks in every layer.

## Scalability Impact

Tenant-scoped tokens and claims scale with the identity provider and are cacheable.

## Cost Impact

Reusing standards (OAuth2/OIDC, KMS, TLS) avoids custom security implementations and compliance rework.

## Operational Impact

Centralized auth, audit, and secret management reduce operational toil and incident response time.

## AI Impact

Model calls are gated by permission checks, ensuring agents cannot access cross-tenant data or privileged actions.

## Reversibility

Medium. The decision can be revisited when validation criteria or operational constraints change; alternatives are documented and can be re-evaluated.
