# ADR-127: Temporal Client Boundary — `packages/temporal-client`

- **ADR ID:** ADR-127
- **Status:** Accepted
- **Group:** Integrations / Temporal Infrastructure
- **Date:** 2026-08-17
- **Decision Owners:** Architecture Review Board, CTO

## Context

Phase 14 Milestone 6 produced a real `TemporalSignalDispatcher` implementing `ITemporalSignalDispatcher` from `packages/outreach`, but it was placed inside `apps/temporal-worker` because that was the first place a Temporal worker existed. The `packages/infrastructure` `IWorkflowClient` and `IWorkflowEngine` ports (Phase 07) also remained without a real implementation.

This created a structural problem: `apps/api` needed to signal (and now start) Temporal workflows, but the real adapter lived inside another application. An app→app dependency would violate the monorepo's package-vs-application layering and force duplicated client construction code across every new entry point.

## Decision

1. Create a new library package `packages/temporal-client` that owns all `@temporalio/client`-backed adapters.
2. The package contains:
   - `TemporalWorkflowClient implements IWorkflowClient` (`packages/infrastructure`) — start, signal, query, and cancel operations.
   - `TemporalSignalDispatcher implements ITemporalSignalDispatcher` (`packages/outreach`) — moved from `apps/temporal-worker/src/infrastructure/`.
3. `packages/temporal-client` depends only on `@temporalio/client` and the two port interfaces above. It contains zero domain or business logic.
4. Both `apps/api` and `apps/temporal-worker` consume `packages/temporal-client`. The copy inside `apps/temporal-worker` is removed.
5. `TemporalWorkflowClient.start()` must:
   - Always receive an explicit `workflowId` (generated by `WorkflowIdFactory`, ADR-126).
   - Use Temporal's `workflowIdReusePolicy: 'REJECT_DUPLICATE'`.
   - Translate `WorkflowExecutionAlreadyStartedError` into an idempotent `ALREADY_RUNNING` result rather than throwing, so callers never see a race condition.

## Alternatives

1. **Keep the real adapters inside `apps/temporal-worker` and give `apps/api` its own duplicate thin client.** Rejected: duplicates connection-management logic and recreates the "multiple conventions" problem at the next layer up.
2. **Implement the adapters directly in `packages/infrastructure`.** Rejected: `packages/infrastructure` is intended for persistence, messaging, and generic infrastructure ports, not a vendor-specific workflow-client SDK. Adding `@temporalio/client` there would leak Temporal details into unrelated consumers.
3. **Expose the adapters through an internal HTTP service from `apps/temporal-worker`.** Rejected: unnecessary operational complexity; Temporal already provides a gRPC client API meant for this purpose.

## Rationale

A dedicated, thin client package isolates the Temporal SDK dependency, gives both applications a single shared implementation, and keeps `packages/infrastructure` provider-neutral. It also matches the repository pattern of separating ports (`packages/infrastructure`) from vendor-specific adapters (a package named after the vendor).

## Consequences

- `apps/temporal-worker` loses its local `temporal-signal-dispatcher.ts`; tests are recreated in `packages/temporal-client`.
- `apps/api` gains a dependency on `packages/temporal-client` for both the webhook reply-dispatch path and the workflow-start path.
- Future workflow engines other than Temporal can be added as additional packages without touching consumers.

## Security Impact

No credentials are stored in workflow state; client connection configuration is injected from environment/secrets providers at application startup.

## Performance Impact

Minimal. The client connection can be cached per process; signal/start calls remain gRPC RPCs either way.

## Risks

- Both apps must depend on the same `packages/temporal-client` version. Mitigation: workspace protocol keeps them aligned.
