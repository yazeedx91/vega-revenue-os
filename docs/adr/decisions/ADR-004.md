# ADR-004: Domain Model and Provider Abstraction

- **ADR ID:** ADR-004
- **Status:** Accepted
- **Group:** Integrations
- **Date:** 2026-08-08
- **Decision Owners:** Architecture Board, CTO

## Context

The AI-Native Autonomous Revenue Employee requires clear integrations direction so that implementation, operations, and future evolution remain coherent. This ADR captures the relevant drivers, alternatives, and consequences for the domain model and provider abstraction concern.

## Problem

Multiple integrations options exist for domain model and provider abstraction. Without a documented decision, individual teams may choose inconsistent technologies or patterns, creating integration debt, security gaps, and operational sprawl.

## Requirements

- Normalize across CRM/ERP providers
- protect core from provider changes
- support adapter addition

## Decision

Define normalized domain objects (Company, Contact, Lead, Opportunity, Activity, Meeting) behind a port/adapter abstraction so the core stays provider-agnostic.

## Alternatives

1. **Use Dynamics 365 entities directly in core business logic**
2. **Build per-provider coupled models without normalization**

## Rationale

Normalized domain objects keep AI and business logic decoupled from Dynamics 365, enabling future CRM/ERP providers to be added without touching the intelligence layer.

## Consequences

This decision aligns the integrations domain with the overall architecture. It enables consistency, reduces cross-cutting risk, and leaves room to revisit alternatives when validation data is available.

## Risks

- Mapping maintenance
- initial modeling overhead

## Mitigations

- Adapter test suites
- versioned schemas
- provider contract tests

## Security Impact

Provider adapters normalize external systems behind domain ports; credentials and tokens are stored in a secrets manager.

## Performance Impact

Caching, idempotency keys, and rate-limiting adapters protect downstream APIs from burst traffic.

## Scalability Impact

New CRM/ERP/email/calendar providers are added as additional adapters, not core changes.

## Cost Impact

Standardized adapters avoid bespoke integrations and enable reuse across tenants.

## Operational Impact

Adapter health and retry metrics are observable; failures are contained within the integration bounded context.

## AI Impact

The intelligence layer receives normalized domain objects, so prompts and planning logic remain provider-agnostic.

## Reversibility

Medium. The decision can be revisited when validation criteria or operational constraints change; alternatives are documented and can be re-evaluated.
