# ADR-005: Event-Driven Architecture

- **ADR ID:** ADR-005
- **Status:** Accepted
- **Group:** Messaging
- **Date:** 2026-08-08
- **Decision Owners:** Architecture Board, CTO

## Context

The AI-Native Autonomous Revenue Employee requires clear messaging direction so that implementation, operations, and future evolution remain coherent. This ADR captures the relevant drivers, alternatives, and consequences for the event-driven architecture concern.

## Problem

Multiple messaging options exist for event-driven architecture. Without a documented decision, individual teams may choose inconsistent technologies or patterns, creating integration debt, security gaps, and operational sprawl.

## Requirements

- Decouple modules
- support mission workflows
- provide reliable delivery
- maintain audit trail

## Decision

Adopt an event-driven architecture with an internal event bus, canonical event schemas, and schema validation for cross-boundary communication.

## Alternatives

1. **Synchronous request/response for all integrations**
2. **Database triggers and polling for state changes**

## Rationale

EDA decouples producers and consumers, supports autonomous agent workflows, and naturally handles external integration events without tight coupling.

## Consequences

This decision aligns the messaging domain with the overall architecture. It enables consistency, reduces cross-cutting risk, and leaves room to revisit alternatives when validation data is available.

## Risks

- Eventual consistency
- debugging complexity
- message ordering

## Mitigations

- Idempotent consumers
- schema registry
- distributed tracing
- compensating actions

## Security Impact

All messages carry tenant identity and are validated at ingress; audit logging is attached to the broker layer.

## Performance Impact

Asynchronous processing decouples producers from consumers, smoothing latency spikes and improving tail latency.

## Scalability Impact

Streams can be partitioned by tenant or by event type to add consumers without blocking producers.

## Cost Impact

Redis Streams reuses the existing Redis footprint; Temporal or Kafka are deferred until workload justifies it.

## Operational Impact

Durable workflows and stream offsets make failure recovery and replay predictable.

## AI Impact

Long-running AI missions and tool calls are staged on streams, allowing agents to resume and report progress.

## Reversibility

Medium. The decision can be revisited when validation criteria or operational constraints change; alternatives are documented and can be re-evaluated.
