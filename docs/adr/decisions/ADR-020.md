# ADR-020: Multi-Model Persistence Strategy

- **ADR ID:** ADR-020
- **Status:** Accepted
- **Group:** Data
- **Date:** 2026-08-08
- **Decision Owners:** Architecture Board, CTO

## Context

The AI-Native Autonomous Revenue Employee requires clear data direction so that implementation, operations, and future evolution remain coherent. This ADR captures the relevant drivers, alternatives, and consequences for the multi-model persistence strategy concern.

## Problem

Multiple data options exist for multi-model persistence strategy. Without a documented decision, individual teams may choose inconsistent technologies or patterns, creating integration debt, security gaps, and operational sprawl.

## Requirements

- Avoid unnecessary store sprawl
- support measured specialization
- keep source of truth clear

## Decision

Adopt a polyglot persistence model only where justified; keep the operational source of truth in PostgreSQL and add specialized stores when measured.

## Alternatives

1. **Single store for every workload**
2. **Many specialized stores from day one**

## Rationale

Starting with one primary store reduces operational complexity. New stores are introduced only after a clear performance or capability bottleneck is measured.

## Consequences

This decision aligns the data domain with the overall architecture. It enables consistency, reduces cross-cutting risk, and leaves room to revisit alternatives when validation data is available.

## Risks

- Later data migrations
- team bias toward trendy stores

## Mitigations

- Clear thresholds for adding stores
- migration path for each new store

## Security Impact

PostgreSQL row-level security, encryption at rest/in transit, and tenant-isolated schemas keep per-tenant data separated.

## Performance Impact

A single operational store with proper indexing, read replicas, and connection pooling supports the common workload efficiently.

## Scalability Impact

PostgreSQL scales vertically and through read replicas; polyglot extensions are introduced only when a clear bottleneck is measured.

## Cost Impact

Using one primary engine reduces licensing and operational overhead compared to a cluster of specialized stores.

## Operational Impact

Managed PostgreSQL or operator-based deployments provide backups, point-in-time recovery, and observability.

## AI Impact

pgvector and JSONB allow documents, vectors, and relational facts to coexist, simplifying retrieval and context assembly.

## Reversibility

Medium. The decision can be revisited when validation criteria or operational constraints change; alternatives are documented and can be re-evaluated.
