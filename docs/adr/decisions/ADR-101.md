# ADR-101: Research Provider Abstraction

- **ADR ID:** ADR-101
- **Status:** Accepted
- **Group:** AI / Intelligence
- **Date:** 2026-08-09
- **Decision Owners:** Architecture Board, CTO

## Context

Intelligence will eventually draw from multiple providers (databases, web indexes, Dynamics 365, job boards). The engine should not depend on any single provider.

## Decision

1. Define `IResearchProvider` with operations: `discoverAccounts`, `getCompanyIntelligence`, `discoverContacts`, `enrichContact`, `detectSignals`.
2. Route provider calls through `IProviderRegistry`, which selects a provider based on tenant config, capability, cost, and reliability.
3. Combine provider results with `IRateLimitStore` to enforce per-tenant/provider quotas.
4. Provide a `StubResearchProvider` for deterministic tests.

## Alternatives

1. Direct provider SDK calls inside agents. Rejected: impossible to swap, mock, or rate-limit uniformly.
2. One giant adapter per provider. Rejected: the common interface lets the engine treat providers as interchangeable data sources.

## Rationale

A provider abstraction keeps the pipeline portable and makes cost/rate-limit control a cross-cutting concern.

## Consequences

- New providers only need an adapter.
- Provider selection can be optimized for cost/coverage.

## Risks

- Provider data shapes differ; the common interface normalizes at the adapter boundary.

## Security Impact

Provider credentials and calls are tenant-scoped and isolated.

## Performance Impact

Provider calls are the bottleneck; abstraction adds negligible overhead.

## Scalability Impact

Rate limiting and caching are centralized per provider.

## Cost Impact

Provider selection and rate limits directly control spend.

## Operational Impact

Operations can enable/disable providers per tenant.

## AI Impact

Agents do not need to know which provider supplied a claim.

## Reversibility

High. New providers are additive.
