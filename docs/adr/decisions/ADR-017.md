# ADR-017: Message Broker

- **ADR ID:** ADR-017
- **Status:** Proposed
- **Group:** Messaging
- **Date:** 2026-08-08
- **Decision Owners:** Architecture Board, CTO

## Context

The AI-Native Autonomous Revenue Employee requires clear messaging direction so that implementation, operations, and future evolution remain coherent. This ADR captures the relevant drivers, alternatives, and consequences for the message broker concern.

## Problem

Multiple messaging options exist for message broker. Without a documented decision, individual teams may choose inconsistent technologies or patterns, creating integration debt, security gaps, and operational sprawl.

## Requirements

- Reliably deliver events
- support multiple consumers
- enable replay
- avoid day-one Kafka complexity

## Decision

Use Redis Streams as the initial message broker; evaluate RabbitMQ, NATS, or Kafka as traffic and durability requirements grow.

## Alternatives

1. **Apache Kafka from day one**
2. **RabbitMQ**

## Rationale

Redis Streams reuses the Redis footprint, has a simple operational model, and is sufficient for early throughput. Kafka is an option when throughput justifies the operational cost.

## Consequences

This decision aligns the messaging domain with the overall architecture. It enables consistency, reduces cross-cutting risk, and leaves room to revisit alternatives when validation data is available.

## Risks

- Durability depends on Redis configuration
- limited ordering guarantees

## Mitigations

- Persistence configuration
- consumer groups
- documented migration path to Kafka

## Security Impact

All messages carry tenant identity and are validated at ingress; audit logging is attached to the broker layer.

## Performance Impact

Asynchronous processing decouples producers from consumers, smoothing latency spikes and improving tail latency.

## Scalability Impact

Streams can be partitioned by tenant or by event type to add consumers without blocking producers.

## Cost Impact

Redis Streams reuses the existing Redis footprint; Temporal or Kafka are deferred until workload justifies it.

## Operational Impact

Durable workflows and stream offsets make failure recovery and replay predictable.

## AI Impact

Long-running AI missions and tool calls are staged on streams, allowing agents to resume and report progress.

## Reversibility

High. The decision can be revisited when validation criteria or operational constraints change; alternatives are documented and can be re-evaluated.
