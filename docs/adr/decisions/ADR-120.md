# ADR-120: Persistence Strategy for Phase 14

- **ADR ID:** ADR-120
- **Status:** Proposed
- **Group:** Data / Infrastructure
- **Date:** 2026-08-13
- **Decision Owners:** Architecture Review Board, CTO, Data Engineering

## Context

All repositories in Phases 08–13 are in-memory doubles (`InMemoryCampaignRepository`, `InMemoryConversationRepository`, `InMemoryMissionRepository`, etc.). Real email requires durable state: sent messages, delivery status, replies, approvals, audit events, idempotency keys, and tenant configuration cannot be lost on restart.

## Decision

1. Phase 14 will introduce **PostgreSQL** as the operational store and **Redis** for cache, rate limiting, and short-lived idempotency.
2. Each bounded context owns its PostgreSQL schema:
   - `outreach` — campaigns, sequences, executions, tenant email config, suppression, allowlist.
   - `conversation` — conversations, reply messages.
   - `mission` — missions, tasks, approvals.
   - `intelligence` — accounts, contacts, leads, evidence, ICP profiles.
   - `audit` — append-only audit log.
   - `idempotency` — idempotency keys.
3. Use snapshot + append-only domain/integration event tables; aggregates load from the latest snapshot plus events since the snapshot.
4. Keep in-memory doubles for deterministic unit tests; integration tests use PostgreSQL/Redis.
5. Schema migrations are owned by each bounded context and applied via a migration tool committed under `infra/database/migrations`.

## Alternatives

1. **Event sourcing as the primary store.** Rejected: too large a shift for Phase 14; snapshot + events gives future event-sourcing compatibility without full infrastructure.
2. **MongoDB or DynamoDB.** Rejected: PostgreSQL provides ACID transactions, RLS for tenant isolation, and JSONB for flexible event payloads with a single operational skill set.
3. **Continue with in-memory stores.** Rejected: state loss is incompatible with real email and audit requirements.

## Rationale

PostgreSQL + Redis is the smallest production-grade stack that satisfies durability, tenant isolation (via RLS), structured querying, and event/audit persistence without introducing new operational complexity.

## Consequences

- Repository ports must be implemented as durable adapters.
- Migration discipline becomes required.
- CI must provision PostgreSQL/Redis for integration tests.
- Event schema stability becomes important for future consumers.
