# ADR-100: Tenant-Isolated Intelligence Memory and Cache

- **ADR ID:** ADR-100
- **Status:** Accepted
- **Group:** AI / Intelligence
- **Date:** 2026-08-09
- **Decision Owners:** Architecture Board, CTO

## Context

Research provider calls are expensive and slow. Caching raw provider results and normalized evidence improves cost and latency, but must never leak data across tenants.

## Decision

1. Introduce `IIntelligenceCache` with tenant-scoped keys, TTL, and explicit invalidation.
2. Cache entries store the provider ID, query hash, cachedAt, and expiresAt.
3. Provider lookup operations always check cache before invoking a provider and only charge cost on cache misses.
4. Implement an in-memory cache for tests and a future Redis/memcached adapter for production.

## Alternatives

1. Cache inside each provider. Rejected: scattered TTLs and no cross-provider reuse.
2. Use the general `packages/infrastructure` cache. Rejected: intelligence cache entries have specific semantics (provider, query hash, freshness) that deserve a dedicated port.

## Rationale

A dedicated tenant-isolated cache keeps cost controls accurate and lets tests verify cache hits/misses deterministically.

## Consequences

- Cost budgets are based on actual provider usage, not cache hits.
- Staleness policies can be tuned per provider.

## Risks

- Stale evidence can mislead scoring; TTLs must be shorter for fast-changing signals than for firmographics.

## Security Impact

Tenant key prefixing prevents accidental cross-tenant cache reads.

## Performance Impact

Significant reduction in provider calls once warm.

## Scalability Impact

A distributed cache is required at scale; the port is already abstracted.

## Cost Impact

Reduces provider spend and improves throughput.

## Operational Impact

Operators can flush cache per tenant or per query pattern.

## AI Impact

Agents can reuse prior research safely within tenant boundaries.

## Reversibility

High. Cache policy changes are configuration-level.
