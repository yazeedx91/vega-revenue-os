# ADR-084: Security and Adversarial Testing

- **ADR ID:** ADR-084
- **Status:** Proposed
- **Group:** Quality
- **Date:** 2026-08-08
- **Decision Owners:** Architecture Board, CTO

## Context

The AI-Native Autonomous Revenue Employee requires clear quality direction so that implementation, operations, and future evolution remain coherent. This ADR captures the relevant drivers, alternatives, and consequences for the security and adversarial testing concern.

## Problem

Multiple quality options exist for security and adversarial testing. Without a documented decision, individual teams may choose inconsistent technologies or patterns, creating integration debt, security gaps, and operational sprawl.

## Requirements

- Scan code
- test dependencies
- red-team AI
- enforce SLAs

## Decision

Run SAST, DAST, dependency scanning, and AI red-teaming in CI with defined fix SLAs.

## Alternatives

1. **No security tests**
2. **Annual penetration test only**

## Rationale

Shifting security and adversarial testing left reduces the cost and risk of vulnerabilities.

## Consequences

This decision aligns the quality domain with the overall architecture. It enables consistency, reduces cross-cutting risk, and leaves room to revisit alternatives when validation data is available.

## Risks

- False positives
- tool overload

## Mitigations

- Severity triage
- slow pipeline for critical

## Security Impact

Security and adversarial tests are part of the quality gate, catching injection, privilege escalation, and data leakage.

## Performance Impact

Contract tests and load tests detect integration and regression performance issues before release.

## Scalability Impact

Automated suites can be parallelized and run against ephemeral environments.

## Cost Impact

Shifting testing left reduces the cost of defects discovered in production.

## Operational Impact

Automated tests and observability-driven quality reduce the manual effort required for releases.

## AI Impact

AI-agent evaluations and red-teaming are codified, so model behavior is measured against a baseline.

## Reversibility

High. The decision can be revisited when validation criteria or operational constraints change; alternatives are documented and can be re-evaluated.
