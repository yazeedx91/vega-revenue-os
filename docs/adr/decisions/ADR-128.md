# ADR-128: Workflow-Start Idempotency Semantics

- **ADR ID:** ADR-128
- **Status:** Accepted
- **Group:** Workflow / Temporal Integration / Outreach
- **Date:** 2026-08-17
- **Decision Owners:** Architecture Review Board, CTO

## Context

Phase 14 Milestone 7 requires that an `OutreachSequence` can be started exactly once as a Temporal workflow. A naive "check whether a workflow exists, then start" approach has a race window and would duplicate the deduplication logic that Temporal already provides via deterministic workflow IDs.

A second concern is auditability: the domain aggregate must know the workflow it is associated with for recovery and tracing, but that persisted link must not become a second, weaker source of truth for uniqueness.

## Decision

1. **Authoritative deduplication is Temporal's `workflowIdReusePolicy`.** `packages/temporal-client`'s `TemporalWorkflowClient.start()` always sets `workflowIdReusePolicy: 'REJECT_DUPLICATE'` and always supplies a deterministic `workflowId` from `WorkflowIdFactory` (ADR-126).
2. **Idempotent start is expressed as a return value, not an exception.** If Temporal responds with `WorkflowExecutionAlreadyStartedError`, the client translates it to `ALREADY_RUNNING` and returns the existing `WorkflowExecutionRef`. Callers treat `STARTED` and `ALREADY_RUNNING` identically for correctness purposes.
3. **The domain aggregate records the link for audit/recovery only.** `OutreachSequence` stores the `workflowId` and emits a `SequenceWorkflowLinked` domain event. This field is optional and additive; it does not participate in the uniqueness decision.
4. **No code path performs a read-then-start check.** Repository lookups of an existing `workflow_id` are for observability, testing, and recovery only, never as a guard before starting.

## Alternatives

1. **Use a database row lock or unique constraint on `outreach.sequences.workflow_id` as the primary dedup mechanism.** Rejected: reimplements what Temporal already guarantees; requires distributed locking and still leaves a Temporal race window open.
2. **Always query Temporal for an existing execution before starting.** Rejected: racy, slower, and still not authoritative compared to `REJECT_DUPLICATE`.
3. **Let the caller catch the raw exception.** Rejected: leaks Temporal SDK details across the `IWorkflowClient` port boundary.

## Rationale

Temporal's deterministic workflow-ID guarantee is the smallest, strongest primitive for exactly-once workflow creation. Wrapping the duplicate-start error into a typed result keeps the port implementation-agnostic while preserving idempotency semantics.

## Consequences

- `IWorkflowClient.start()` return type and `WorkflowStartOptions` must support an explicit `workflowId` and communicate idempotent duplicates.
- Tests must assert that a second start returns `ALREADY_RUNNING` and does not create a second workflow.
- Crash/restart recovery works by recomputing the same workflow ID and relying on Temporal to identify the existing run.

## Security Impact

None beyond what is covered by ADR-126's tenant-scoped ID scheme.
