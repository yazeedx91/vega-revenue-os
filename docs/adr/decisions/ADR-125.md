# ADR-125: Business-System Connector Abstraction (IBusinessSystemConnector)

- **ADR ID:** ADR-125
- **Status:** Accepted
- **Group:** Integrations / Domain Architecture
- **Date:** 2026-08-17
- **Decision Owners:** Architecture Review Board, CTO

## Context

The platform's strategic objective has been generalized: ProjectX is an AI-Native Autonomous Revenue Employee that must operate against ERP systems, CRM systems, industrial/customer-centric applications, and custom business applications — not exclusively Microsoft Dynamics 365. Dynamics 365 must be the **first connector**, not the architectural center.

Investigation (Phase 13.5 architecture review) found the core domain (`Company`, `Contact`, `Lead`, `Opportunity`, `Meeting`, `Evidence`, `BuyingSignal`) was already provider-neutral, consistent with `DD-004` and the existing ACL docs (`docs/domain/17-external-system-boundaries.md`, `docs/domain/18-anti-corruption-layers.md`). The only concrete coupling was naming: `IDynamicsIntelligenceAdapter` in `packages/intelligence` named a provider-neutral read-side contract after its first implementation.

## Decision

1. Define a canonical, capability-based abstraction: `IBusinessSystemConnector`. A connector exposes business **capabilities** (e.g. `searchAccounts`, `getAccount`, `searchContacts`, `getContact`, `createLead`, `updateLead`, `getOpportunity`, `createActivity`, `getCustomer`, `searchBusinessEvents`, `getOperationalSignals`) rather than vendor-specific APIs. Not every connector implements every capability.
2. Each connector declares a capability descriptor for discovery: provider, system type, version, capabilities, readable/writable entities, authentication model, event support, webhook support, rate limits, tenant configuration.
3. Relationship chain: **Canonical Domain → IBusinessSystemConnector → Provider Connector (e.g. Dynamics365Connector) → Customer System (e.g. Dataverse)**.
4. The existing intelligence-scoped read port is renamed from `IDynamicsIntelligenceAdapter` to `IBusinessSystemIntelligenceAdapter` (`packages/intelligence/src/ports/business-system-intelligence.interface.ts`). This is the read-side slice of the eventual full connector for account/contact lookup and duplicate detection. `StubDynamicsIntelligenceAdapter` is renamed to `DynamicsIntelligenceAdapterStub`, remaining the first concrete (stub) implementation.
5. `ResearchEngine`'s dependency is renamed from `dynamicsAdapter` to `businessSystemAdapter`.
6. Industrial/operational data (assets, operational events, service records, maintenance events, production signals) enters the intelligence architecture as normalized `BuyingSignal` / `ResearchEvidence` records via `searchBusinessEvents` / `getOperationalSignals` — never as raw vendor payloads, and never as new core domain aggregates.
7. The full `packages/business-systems` package (multi-connector registry, capability discovery runtime, `Dynamics365Connector` implementation) is **designed but not implemented** in this ADR. It is scoped for a future, separately approved phase.
8. `ICRMProvider` (`packages/infrastructure/src/crm/crm.interface.ts`) is identified as a precursor candidate for the eventual `IBusinessSystemConnector` implementation; it is unused today and not modified by this ADR.

## Alternatives

1. **Keep Dynamics-named interfaces and treat Dynamics as the permanent architectural center.** Rejected: contradicts the new strategic objective and blocks Salesforce/SAP/industrial-application connectors without a rewrite.
2. **Build a single universal enterprise data model spanning all provider concepts.** Rejected: recreates the "provider concepts leak into core domain" failure mode `DD-004` already rejected; increases core domain complexity for capabilities most tenants will never use.
3. **Implement the full `packages/business-systems` connector runtime now, including Salesforce/SAP stubs.** Rejected: out of scope; premature before the abstraction shape is proven against a second real connector.

## Rationale

A capability-based connector abstraction lets the platform declare what a given customer's business system can do without assuming every system supports every operation — critical for supporting industrial/custom applications that may only support read-side operational signals, not full CRM write-back. Keeping this ADR to a rename plus a documented design (not a new package) avoids scope creep while unblocking the strategic repositioning.

## Consequences

- `packages/intelligence` no longer has a Dynamics-named contract; `IBusinessSystemIntelligenceAdapter` and `DynamicsIntelligenceAdapterStub` reflect the connector relationship directly.
- `ResearchEngine` behavior is unchanged; only the dependency name changed.
- Future CRM/ERP/industrial connectors are added as new implementations of `IBusinessSystemConnector` (or its read-side slice) without touching `ResearchEngine` or core domain aggregates.
- `packages/business-systems` remains an open follow-up item pending separate ARB approval.

## Risks

- Naming drift if a future full `IBusinessSystemConnector` package diverges from the shape described here — mitigated by treating this ADR as the canonical reference to update, not replace, when that package is implemented.

## Security Impact

No change. Credentials remain in the secrets manager; no new external calls are introduced.

## Performance Impact

None. Rename only; no runtime behavior change.

## Scalability Impact

Positive. New business-system connectors (Salesforce, SAP, custom industrial applications) can be added as new implementations without core domain or `ResearchEngine` changes.

## Cost Impact

None in this phase.

## Operational Impact

None in this phase; no new services or infrastructure introduced.

## AI Impact

None. The intelligence layer continues to receive normalized domain objects and evidence, unaffected by the connector naming.

## Reversibility

High. The interface/class rename is a pure refactor; reverting is a mechanical inverse rename.
