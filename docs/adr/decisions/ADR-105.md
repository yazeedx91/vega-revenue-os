# ADR-105: Outreach Aggregate Decomposition

- **ADR ID:** ADR-105
- **Status:** Proposed
- **Group:** AI / Outreach
- **Date:** 2026-08-12
- **Decision Owners:** Architecture Review Board, CTO

## Context

Outreach execution involves campaigns, sequences, messages, and individual sends. We need to decide which concepts are aggregate roots versus value objects/entities to keep transactional boundaries clear.

## Decision

1. `OutreachCampaign` is an aggregate root. It owns campaign-level policy, budget, channel strategy, and high-level lifecycle.
2. `OutreachSequence` is an aggregate root per recipient. It owns step progression, scheduling state, and per-recipient lifecycle.
3. `OutreachMessageExecution` is an aggregate root per send attempt. It owns provider interaction state, idempotency, retry history, and final delivery status.
4. `SequenceStep`, `Recipient`, and `MessageDraft` are value objects/entities within the `OutreachSequence` aggregate.
5. Campaigns reference sequences by ID; sequences reference executions by ID. Cross-aggregate consistency is eventual via domain events.

## Alternatives

1. One giant `OutreachCampaign` aggregate containing all sequences and sends. Rejected: large concurrency and storage burden; every send would lock the entire campaign.
2. `OutreachMessageExecution` as an entity inside `OutreachSequence`. Rejected: send attempts require independent idempotency, retry, and provider reconciliation that do not need to lock the whole sequence.
3. `OutreachSequence` as a value object inside `OutreachCampaign`. Rejected: per-recipient progression and pause/resume are mutable stateful lifecycles.

## Rationale

Three small aggregate roots provide clear transactional boundaries: campaign policy, sequence progression, and send execution can evolve independently while communicating through events and IDs.

## Consequences

- Campaign completion is derived from sequence states, not a single aggregate lock.
- Idempotency and retry logic live naturally with the execution aggregate.
- Eventual consistency must be handled for campaign-wide metrics and budget enforcement.

## Risks

- Over-splitting could complicate campaign-level invariants (e.g., `maxOutreachCount`). Mitigated by campaign-level counters updated via events or by querying sequence repository within application services.

## Security Impact

No new security impact; each aggregate carries its `tenantId`.

## Performance Impact

Positive; per-recipient sequences and per-send executions can be processed in parallel.

## Scalability Impact

Positive; aggregates can be sharded by recipient/execution.

## Cost Impact

None.

## Operational Impact

Operations can inspect a single execution for full send traceability.

## AI Impact

Personalization results are stored inside `MessageDraft` value objects; no direct AI impact.

## Reversibility

Medium. Splitting or merging aggregates later requires event migration but does not affect external provider contracts.
