# ADR-014: Knowledge Graph Storage

- **ADR ID:** ADR-014
- **Status:** Proposed
- **Group:** Data
- **Date:** 2026-08-08
- **Decision Owners:** Architecture Board, CTO

## Context

The AI-Native Autonomous Revenue Employee requires clear data direction so that implementation, operations, and future evolution remain coherent. This ADR captures the relevant drivers, alternatives, and consequences for the knowledge graph storage concern.

## Problem

Multiple data options exist for knowledge graph storage. Without a documented decision, individual teams may choose inconsistent technologies or patterns, creating integration debt, security gaps, and operational sprawl.

## Requirements

- Model relationships and entities
- support graph queries
- avoid lock-in

## Decision

Use a property graph layer on PostgreSQL/Aurora initially; Neo4j is an optional future path when graph workloads dominate.

## Alternatives

1. **Neo4j as the primary store**
2. **No graph model; use only relational tables**

## Rationale

A property graph on the existing store defers additional operational complexity while enabling relationship-centric queries. Neo4j can be adopted if graph load justifies it.

## Consequences

This decision aligns the data domain with the overall architecture. It enables consistency, reduces cross-cutting risk, and leaves room to revisit alternatives when validation data is available.

## Risks

- Graph schema complexity
- query optimization
- migration effort

## Mitigations

- Abstract graph interface
- feature flags
- clear expansion criteria

## Security Impact

PostgreSQL row-level security, encryption at rest/in transit, and tenant-isolated schemas keep per-tenant data separated.

## Performance Impact

A single operational store with proper indexing, read replicas, and connection pooling supports the common workload efficiently.

## Scalability Impact

PostgreSQL scales vertically and through read replicas; polyglot extensions are introduced only when a clear bottleneck is measured.

## Cost Impact

Using one primary engine reduces licensing and operational overhead compared to a cluster of specialized stores.

## Operational Impact

Managed PostgreSQL or operator-based deployments provide backups, point-in-time recovery, and observability.

## AI Impact

pgvector and JSONB allow documents, vectors, and relational facts to coexist, simplifying retrieval and context assembly.

## Reversibility

High. The decision can be revisited when validation criteria or operational constraints change; alternatives are documented and can be re-evaluated.
