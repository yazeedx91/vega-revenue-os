# ADR-021: Mission Workflow Processing

- **ADR ID:** ADR-021
- **Status:** Accepted
- **Group:** Messaging
- **Date:** 2026-08-08
- **Decision Owners:** Architecture Board, CTO

## Context

The AI-Native Autonomous Revenue Employee requires clear messaging direction so that implementation, operations, and future evolution remain coherent. This ADR captures the relevant drivers, alternatives, and consequences for the mission workflow processing concern.

## Problem

Multiple messaging options exist for mission workflow processing. Without a documented decision, individual teams may choose inconsistent technologies or patterns, creating integration debt, security gaps, and operational sprawl.

## Requirements

- Represent long-running work
- support retries and compensation
- provide observability

## Decision

Model revenue employee tasks as durable, observable missions with explicit states, checkpoints, and compensation actions.

## Alternatives

1. **Ad-hoc script orchestration**
2. **Pure chat-style interaction without workflow boundaries**

## Rationale

A mission abstraction gives autonomous work clear state, retry semantics, and audit boundaries, aligning with the product purpose.

## Consequences

This decision aligns the messaging domain with the overall architecture. It enables consistency, reduces cross-cutting risk, and leaves room to revisit alternatives when validation data is available.

## Risks

- Over-specification
- user friction
- mission bloat

## Mitigations

- Mission templates and defaults
- human override
- progress reporting

## Security Impact

All messages carry tenant identity and are validated at ingress; audit logging is attached to the broker layer.

## Performance Impact

Asynchronous processing decouples producers from consumers, smoothing latency spikes and improving tail latency.

## Scalability Impact

Streams can be partitioned by tenant or by event type to add consumers without blocking producers.

## Cost Impact

Redis Streams reuses the existing Redis footprint; Temporal or Kafka are deferred until workload justifies it.

## Operational Impact

Durable workflows and stream offsets make failure recovery and replay predictable.

## AI Impact

Long-running AI missions and tool calls are staged on streams, allowing agents to resume and report progress.

## Reversibility

Medium. The decision can be revisited when validation criteria or operational constraints change; alternatives are documented and can be re-evaluated.
