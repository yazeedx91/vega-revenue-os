# ADR-107: Outreach Idempotency and Exactly-Once Send Protection

- **ADR ID:** ADR-107
- **Status:** Proposed
- **Group:** AI / Outreach
- **Date:** 2026-08-12
- **Decision Owners:** Architecture Review Board, CTO

## Context

Outreach sends must not be duplicated when a workflow retries, an activity retries, a provider times out after accepting a request, or Temporal replays. Idempotency must be deterministic and auditable.

## Decision

1. Use two layers of idempotency:
   - **Application command layer:** existing `IIdempotencyStore` prevents duplicate top-level commands.
   - **Provider send layer:** each `OutreachMessageExecution` carries a deterministic `idempotencyKey` persisted before any provider call.
2. The provider-level key is deterministic and stable across retries:
   ```
   outreach:{tenantId}:{campaignId}:{sequenceId}:{stepIndex}:{recipientHash}:{channel}:{providerId}
   ```
3. Before calling a provider, the execution service checks whether an existing `OutreachMessageExecution` with the same key has already reached `SUBMITTED` or later. If so, it returns the stored result instead of resending.
4. Provider acceptance (`SUBMITTED` → `ACCEPTED`) is treated as a terminal commitment. Failures after acceptance are recorded as state updates, not rollbacks.
5. Idempotency keys are included in audit records and telemetry tags.

## Alternatives

1. Rely solely on the application command idempotency store. Rejected: a single command can span multiple provider calls and workflow replays; provider-level keys are needed for each logical send.
2. Use UUIDs for idempotency keys. Rejected: UUIDs change on retry and cannot protect against replays or timeout-after-acceptance.

## Rationale

Deterministic keys tied to business identity (campaign, sequence, step, recipient, channel, provider) make each logical send unique and replay-safe without requiring a central lock.

## Consequences

- Duplicate sends are prevented even when provider responses are lost.
- The execution aggregate becomes the source of truth for send state.
- Key collisions across different business intents are avoided by including step index and channel.

## Risks

- If business identity changes (e.g., sequence split), the key generation must change in a backward-compatible way.
- Key length is bounded; recipient hash should be stable.

## Security Impact

Idempotency keys contain tenant/campaign identifiers but no PII; stored in tenant-scoped repositories.

## Performance Impact

Minimal; key lookup is by tenant-scoped repository.

## Scalability Impact

Positive; no global lock required.

## Cost Impact

None.

## Operational Impact

Operators can trace a send across retries using the idempotency key.

## AI Impact

None.

## Reversibility

Medium. Changing key generation requires migration of existing execution records.
