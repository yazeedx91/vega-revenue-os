# ADR-096: Mission Orchestrator Package & Temporal Activity Boundaries

- **ADR ID:** ADR-096
- **Status:** Accepted
- **Group:** AI / Workflow
- **Date:** 2026-08-08
- **Decision Owners:** Architecture Board, CTO

## Context

Phase 09 delivered an AI Execution Kernel that can run a single agent task but does not coordinate multi-step missions across approval gates, failures, retries, compensation, and recovery. Phase 10 needs a durable runtime that can drive the existing `Mission` aggregate without changing its ownership of business state.

Temporal was already selected as the workflow engine in ADR-018. The open questions were:

1. Where does the orchestration logic live?
2. How is it tested without a Temporal server?
3. How do human approvals fit into the domain model?

## Decision

1. Create a dedicated `packages/mission-orchestrator` package that contains:
   - The orchestration engine (`MissionExecutionEngine`).
   - A new `Approval` domain aggregate.
   - Repository and integration ports with in-memory doubles.
   - Activity functions that wrap the engine.
2. Keep workflow logic out of the domain layer. `Mission` and `MissionTask` remain the sole owners of lifecycle state.
3. Define a thin workflow port in `packages/infrastructure` (`IWorkflowClient`/`IWorkflowEngine`). The orchestrator service depends on the port; the Temporal adapter lives in the Temporal worker app.
4. Place the Temporal workflow definition in `apps/temporal-worker/src/workflows/mission-workflow.ts` and register it in `apps/temporal-worker/src/main.ts`.
5. Implement human approvals as a first-class `Approval` aggregate with its own status machine and events, not as workflow side effects.

## Alternatives

1. Put the workflow directly inside the `Mission` aggregate. Rejected because it would couple domain state to Temporal concepts.
2. Use a custom workflow engine instead of Temporal. Rejected; ADR-018 already selected Temporal for durability and observability.
3. Implement approvals as workflow signals only. Rejected because human decisions must be auditable domain events.

## Rationale

A dedicated orchestrator package with clear ports keeps the domain pure, makes the orchestration logic testable without infrastructure, and aligns with the existing port/adapter architecture.

## Consequences

- The orchestrator is testable deterministically with in-memory doubles.
- Temporal-specific code is isolated in the worker app, making the orchestrator portable.
- The `Approval` aggregate adds a small new bounded context but keeps audit and state ownership clear.
- Mission aggregate state transitions remain the single source of truth for the business lifecycle.

## Risks

- The workflow definition is currently a deterministic skeleton; production must expand the loop to select actual tasks from the aggregate.
- Activity context uses a module-level engine binding for simplicity; future iterations should use a factory that receives tenant-scoped dependencies.

## Security Impact

Tenant isolation is enforced at every boundary: repository keys, command handlers, and workflow input all require a `tenantId`.

## Performance Impact

No additional runtime overhead beyond the Temporal worker; in-memory doubles are used only in tests.

## Scalability Impact

Temporal workers can scale horizontally. Mission state is reconstructed from repository snapshots and workflow history rather than held in the worker.

## Cost Impact

Minimal additional cost; Temporal Cloud or self-hosted Temporal is already assumed by ADR-018.

## Operational Impact

The worker application logs task-queue registration and delegates all business logic to the engine, keeping operational surface small.

## AI Impact

The orchestrator enables multi-step, long-running AI missions with safe pause/resume and human approval gates.

## Reversibility

Medium. The package can be refactored or replaced as long as the port contracts remain stable.
