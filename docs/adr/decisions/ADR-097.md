# ADR-097: Revenue Intelligence Package Boundary

- **ADR ID:** ADR-097
- **Status:** Accepted
- **Group:** AI / Intelligence
- **Date:** 2026-08-09
- **Decision Owners:** Architecture Board, CTO

## Context

Phase 11 introduces revenue intelligence, lead generation, and research capabilities. We need to decide where the new bounded context lives without duplicating the Phase 10 orchestrator or polluting unrelated packages.

## Decision

1. Core intelligence domain entities (`ICPProfile`, `Account`, `Contact`, `Lead`, `ResearchEvidence`) live in `packages/domain` so they share the same aggregate/event conventions as `Mission` and `Approval`.
2. Research engines, specialist agents, scoring, provider adapters, and integration services live in a new `packages/intelligence` package.
3. `packages/intelligence` depends on `packages/domain`, `packages/infrastructure`, `packages/ai-runtime`, and `packages/shared` only. It does **not** depend on `packages/mission-orchestrator`.
4. Mission orchestration integration is achieved by injecting intelligence agents/executors into the Phase 10 `MissionExecutionEngine` at wiring time.

## Alternatives

1. Put everything in `packages/ai-runtime`. Rejected: intelligence has its own aggregates and provider concerns that would overload the execution kernel.
2. Create a large new package that owns domain entities too. Rejected: domain consistency is easier when all aggregates share one package and one event/versioning style.

## Rationale

Domain entities stay co-located with existing aggregates, while the new bounded context has a dedicated home for research-specific services, ports, and stubs. This avoids a circular dependency between intelligence and orchestration.

## Consequences

- `packages/intelligence` can be tested in isolation.
- The orchestrator remains generic; intelligence capabilities are added by registering agents/planner templates.
- A shared `packages/domain` dependency means domain changes affect both contexts, which is acceptable for a single product team.

## Risks

- The new package may grow; future decomposition can split it by provider or subdomain if needed.

## Security Impact

No direct security impact; tenant isolation remains at the domain/repository boundary.

## Performance Impact

Minimal; package boundary is compile-time only.

## Scalability Impact

Positive: the intelligence engine can be deployed as its own worker pool behind a well-defined port if needed.

## Cost Impact

None.

## Operational Impact

None.

## AI Impact

Enables a dedicated, testable AI-native research and scoring layer.

## Reversibility

Medium. Entities can be moved, but the public port/adapter surface of `packages/intelligence` is small enough to refactor later.
