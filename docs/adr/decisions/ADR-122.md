# ADR-122: Suppression and Opt-Out Model

- **ADR ID:** ADR-122
- **Status:** Proposed
- **Group:** Outreach / Compliance / Conversation
- **Date:** 2026-08-13
- **Decision Owners:** Architecture Review Board, CTO, Legal/Compliance

## Context

Real email requires compliance with opt-out laws and tenant policies. The system must not send to prospects who have opted out, and it must record opt-outs durably.

## Decision

1. Maintain a per-tenant **suppression list** containing opted-out email addresses and domains.
2. A prospect can be suppressed by:
   - Clicking an unsubscribe link.
   - Replying with opt-out language (e.g., "unsubscribe", "opt out", "stop").
   - Manual admin action.
3. `OutreachExecutionService` must check the suppression list before drafting any message.
4. `Conversation` aggregate already recognizes opt-out language (`packages/domain/src/conversation/conversation.ts:108-120`); the conversation service must record the suppression entry.
5. Suppression entries are append-only and audited; removal requires admin action with justification.

## Alternatives

1. **Hard-delete suppression entries.** Rejected: destroys compliance evidence and audit trail.
2. **Global suppression list shared across tenants.** Rejected: violates tenant isolation.
3. **Defer suppression to CRM.** Rejected: ProjectX is the system of record for email interactions in Phase 14; CRM write-back is deferred.

## Rationale

A tenant-scoped, append-only suppression list is the minimum viable compliance control for outbound email. It integrates cleanly with the existing `Conversation` opt-out detection and the `OutreachExecutionService` pre-send checks.

## Consequences

- `ISuppressionListRepository` and `SuppressionService` must be added.
- Every send path must check suppression before provider invocation.
- Opt-out link generation is required for outbound emails.
- Suppression audits become part of compliance reporting.
