# ADR-015: Caching, Conversation, and Session Store

- **ADR ID:** ADR-015
- **Status:** Proposed
- **Group:** Data
- **Date:** 2026-08-08
- **Decision Owners:** Architecture Board, CTO

## Context

The AI-Native Autonomous Revenue Employee requires clear data direction so that implementation, operations, and future evolution remain coherent. This ADR captures the relevant drivers, alternatives, and consequences for the caching, conversation, and session store concern.

## Problem

Multiple data options exist for caching, conversation, and session store. Without a documented decision, individual teams may choose inconsistent technologies or patterns, creating integration debt, security gaps, and operational sprawl.

## Requirements

- Cache API data
- store sessions
- support conversation state
- enable rate limiting

## Decision

Use Redis for caches, agent conversation state, sessions, and rate limiting.

## Alternatives

1. **Memcached for caching only**
2. **Custom in-memory cache**

## Rationale

Redis supports structures, TTL, pub/sub, and Streams within a single operational footprint, making it versatile for session and agent state.

## Consequences

This decision aligns the data domain with the overall architecture. It enables consistency, reduces cross-cutting risk, and leaves room to revisit alternatives when validation data is available.

## Risks

- Single point of failure
- data loss on restart
- operational complexity

## Mitigations

- Redis Sentinel or Cluster
- persistence for important data
- short TTL for transient sessions

## Security Impact

PostgreSQL row-level security, encryption at rest/in transit, and tenant-isolated schemas keep per-tenant data separated.

## Performance Impact

A single operational store with proper indexing, read replicas, and connection pooling supports the common workload efficiently.

## Scalability Impact

PostgreSQL scales vertically and through read replicas; polyglot extensions are introduced only when a clear bottleneck is measured.

## Cost Impact

Using one primary engine reduces licensing and operational overhead compared to a cluster of specialized stores.

## Operational Impact

Managed PostgreSQL or operator-based deployments provide backups, point-in-time recovery, and observability.

## AI Impact

pgvector and JSONB allow documents, vectors, and relational facts to coexist, simplifying retrieval and context assembly.

## Reversibility

High. The decision can be revisited when validation criteria or operational constraints change; alternatives are documented and can be re-evaluated.
