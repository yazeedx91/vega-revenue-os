# ADR-119: Allowlist-Only Rollout Model for Phase 14 Email

- **ADR ID:** ADR-119
- **Status:** Proposed
- **Group:** Outreach / Safety / Operations
- **Date:** 2026-08-13
- **Decision Owners:** Architecture Review Board, CTO, Security

## Context

Phase 14 is the first time ProjectX will send real email to real recipients. Unrestricted sending would create legal, compliance, reputation, and safety risks before the system is validated.

## Decision

1. All real email sends in Phase 14 MUST target recipients explicitly present in a per-tenant `AllowedRecipient` list.
2. A send to any non-allowlisted recipient is blocked, audited, and fails with a clear error.
3. Allowlist additions and removals require an admin role and are themselves audited.
4. Transition from allowlist-only to broader rollout requires an explicit ARB/Security review and updated ADR.
5. The rollout model is:
   - **ALLOWLIST-ONLY** → **VALIDATION** → **ARB/GO-LIVE REVIEW** → **CONTROLLED EXPANSION**

## Alternatives

1. **Unrestricted sends from day one.** Rejected: unacceptable compliance and reputation risk.
2. **Rate-limit only without allowlist.** Rejected: rate limits reduce volume but do not prevent sends to wrong recipients.
3. **Domain-based allowlist only.** Rejected: too coarse; individual recipient control is required for early validation.

## Rationale

An explicit per-recipient allowlist is the strongest safety boundary for a first real integration. It lets the team validate provider behavior, delivery tracking, reply ingestion, and end-to-end flow with a small, known set of recipients.

## Consequences

- `TenantEmailConfigurationService` and `IAllowedRecipientRepository` must be implemented.
- `OutreachExecutionService` must check the allowlist before calling the provider.
- Every allowlist mutation produces an audit event.
- Sales/marketing onboarding must include an allowlist management step.
