# ADR-008: Backend and Frontend Separation

- **ADR ID:** ADR-008
- **Status:** Accepted
- **Group:** Presentation
- **Date:** 2026-08-08
- **Decision Owners:** Architecture Board, CTO

## Context

The AI-Native Autonomous Revenue Employee requires clear presentation direction so that implementation, operations, and future evolution remain coherent. This ADR captures the relevant drivers, alternatives, and consequences for the backend and frontend separation concern.

## Problem

Multiple presentation options exist for backend and frontend separation. Without a documented decision, individual teams may choose inconsistent technologies or patterns, creating integration debt, security gaps, and operational sprawl.

## Requirements

- Centralize business logic
- support multiple clients
- enforce policies in one place

## Decision

Separate the backend API from the web frontend; the backend owns all intelligence, integrations, and policies.

## Alternatives

1. **Full-stack server-rendered application**
2. **Thick client with direct external API calls**

## Rationale

A clear backend/frontend split improves security, enables multi-channel clients, and centralizes authorization and audit.

## Consequences

This decision aligns the presentation domain with the overall architecture. It enables consistency, reduces cross-cutting risk, and leaves room to revisit alternatives when validation data is available.

## Risks

- API roundtrips
- state management complexity

## Mitigations

- Backend-for-frontend layer where needed
- caching
- optimistic UI updates

## Security Impact

The presentation layer delegates all sensitive logic to the backend, keeping tokens and policies enforceable in a single trust boundary.

## Performance Impact

API-first design lets front-ends and clients load only what they need and cache state independently.

## Scalability Impact

REST/GraphQL can be scaled behind load balancers and CDN; the backend can evolve without UI rewrites.

## Cost Impact

Reusing API contracts for web and integrations avoids duplicating implementation effort.

## Operational Impact

Standard HTTP tooling, OpenAPI specs, and client generation simplify debugging and onboarding.

## AI Impact

UI components can request structured AI payloads through the same API contracts, ensuring consistent validation.

## Reversibility

Medium. The decision can be revisited when validation criteria or operational constraints change; alternatives are documented and can be re-evaluated.
