# ADR-010: API Protocol

- **ADR ID:** ADR-010
- **Status:** Proposed
- **Group:** Presentation
- **Date:** 2026-08-08
- **Decision Owners:** Architecture Board, CTO

## Context

The AI-Native Autonomous Revenue Employee requires clear presentation direction so that implementation, operations, and future evolution remain coherent. This ADR captures the relevant drivers, alternatives, and consequences for the api protocol concern.

## Problem

Multiple presentation options exist for api protocol. Without a documented decision, individual teams may choose inconsistent technologies or patterns, creating integration debt, security gaps, and operational sprawl.

## Requirements

- Serve web and integration clients
- support aggregation
- avoid unnecessary protocol complexity

## Decision

Use HTTP/REST with JSON for standard CRUD and synchronous operations; add GraphQL for complex aggregated reads; gRPC reserved for future internal high-throughput paths.

## Alternatives

1. **GraphQL for every endpoint**
2. **gRPC and REST mixed from day one**

## Rationale

REST keeps the API simple and broadly supported. GraphQL can optimize front-end queries. gRPC adds operational complexity that is not justified at launch.

## Consequences

This decision aligns the presentation domain with the overall architecture. It enables consistency, reduces cross-cutting risk, and leaves room to revisit alternatives when validation data is available.

## Risks

- Multiple protocol support
- caching differences
- tooling sprawl

## Mitigations

- Gateway normalization
- documented use cases per protocol
- client generation

## Security Impact

The presentation layer delegates all sensitive logic to the backend, keeping tokens and policies enforceable in a single trust boundary.

## Performance Impact

API-first design lets front-ends and clients load only what they need and cache state independently.

## Scalability Impact

REST/GraphQL can be scaled behind load balancers and CDN; the backend can evolve without UI rewrites.

## Cost Impact

Reusing API contracts for web and integrations avoids duplicating implementation effort.

## Operational Impact

Standard HTTP tooling, OpenAPI specs, and client generation simplify debugging and onboarding.

## AI Impact

UI components can request structured AI payloads through the same API contracts, ensuring consistent validation.

## Reversibility

High. The decision can be revisited when validation criteria or operational constraints change; alternatives are documented and can be re-evaluated.
