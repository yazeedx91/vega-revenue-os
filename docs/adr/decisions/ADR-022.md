# ADR-022: Event Streaming versus Event Sourcing

- **ADR ID:** ADR-022
- **Status:** Proposed
- **Group:** Messaging
- **Date:** 2026-08-08
- **Decision Owners:** Architecture Board, CTO

## Context

The AI-Native Autonomous Revenue Employee requires clear messaging direction so that implementation, operations, and future evolution remain coherent. This ADR captures the relevant drivers, alternatives, and consequences for the event streaming versus event sourcing concern.

## Problem

Multiple messaging options exist for event streaming versus event sourcing. Without a documented decision, individual teams may choose inconsistent technologies or patterns, creating integration debt, security gaps, and operational sprawl.

## Requirements

- Capture state changes
- support audit
- avoid unnecessary operational burden

## Decision

Use event streaming and state snapshots; adopt event sourcing only for mission history and audit contexts.

## Alternatives

1. **Full event sourcing across all services**
2. **No events; direct state mutations only**

## Rationale

Event streaming is simpler to operate than full event sourcing while still capturing an audit trail. Full event sourcing adds complexity that is not broadly required.

## Consequences

This decision aligns the messaging domain with the overall architecture. It enables consistency, reduces cross-cutting risk, and leaves room to revisit alternatives when validation data is available.

## Risks

- Snapshot consistency
- storage growth
- reconstruction complexity

## Mitigations

- Compaction
- retention policies
- source-of-truth in PostgreSQL
- event schema registry

## Security Impact

All messages carry tenant identity and are validated at ingress; audit logging is attached to the broker layer.

## Performance Impact

Asynchronous processing decouples producers from consumers, smoothing latency spikes and improving tail latency.

## Scalability Impact

Streams can be partitioned by tenant or by event type to add consumers without blocking producers.

## Cost Impact

Redis Streams reuses the existing Redis footprint; Temporal or Kafka are deferred until workload justifies it.

## Operational Impact

Durable workflows and stream offsets make failure recovery and replay predictable.

## AI Impact

Long-running AI missions and tool calls are staged on streams, allowing agents to resume and report progress.

## Reversibility

High. The decision can be revisited when validation criteria or operational constraints change; alternatives are documented and can be re-evaluated.
