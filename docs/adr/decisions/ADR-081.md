# ADR-081: Contract and API Testing

- **ADR ID:** ADR-081
- **Status:** Accepted
- **Group:** Quality
- **Date:** 2026-08-08
- **Decision Owners:** Architecture Board, CTO

## Context

The AI-Native Autonomous Revenue Employee requires clear quality direction so that implementation, operations, and future evolution remain coherent. This ADR captures the relevant drivers, alternatives, and consequences for the contract and api testing concern.

## Problem

Multiple quality options exist for contract and api testing. Without a documented decision, individual teams may choose inconsistent technologies or patterns, creating integration debt, security gaps, and operational sprawl.

## Requirements

- Verify API contracts
- detect breaking changes
- validate specs

## Decision

Use Pact or Schemathesis for contract tests and validate OpenAPI/AsyncAPI specs in CI.

## Alternatives

1. **No contract tests**
2. **Postman collections only**

## Rationale

Contract tests catch integration mismatches early and keep consumers and providers aligned.

## Consequences

This decision aligns the quality domain with the overall architecture. It enables consistency, reduces cross-cutting risk, and leaves room to revisit alternatives when validation data is available.

## Risks

- Contract maintenance
- false negatives

## Mitigations

- Consumer-driven contracts
- CI gate

## Security Impact

Security and adversarial tests are part of the quality gate, catching injection, privilege escalation, and data leakage.

## Performance Impact

Contract tests and load tests detect integration and regression performance issues before release.

## Scalability Impact

Automated suites can be parallelized and run against ephemeral environments.

## Cost Impact

Shifting testing left reduces the cost of defects discovered in production.

## Operational Impact

Automated tests and observability-driven quality reduce the manual effort required for releases.

## AI Impact

AI-agent evaluations and red-teaming are codified, so model behavior is measured against a baseline.

## Reversibility

Medium. The decision can be revisited when validation criteria or operational constraints change; alternatives are documented and can be re-evaluated.
