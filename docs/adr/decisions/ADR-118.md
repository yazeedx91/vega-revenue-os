# ADR-118: Microsoft Graph / Exchange Online as Primary Email Provider

- **ADR ID:** ADR-118
- **Status:** Proposed
- **Group:** Outreach / Integration
- **Date:** 2026-08-13
- **Decision Owners:** Architecture Review Board, CTO

## Context

Phase 12 defined the `IEmailProvider` port and `StubEmailProvider` (`packages/outreach/src/infrastructure/stub-email-provider.ts`). Phase 14 needs a real email provider. The choices include Microsoft Graph/Exchange Online, SendGrid, AWS SES, or a generic SMTP relay.

## Decision

1. Use **Microsoft Graph / Exchange Online** as the primary email provider for Phase 14.
2. Implement the provider behind the existing `IEmailProvider` / `IOutreachProvider` ports so future providers can be swapped in without changing domain logic.
3. Defer SendGrid, AWS SES, and other SMTP providers to a later phase.
4. Defer LinkedIn messaging and calendar providers; `StubCalendarProvider` and `StubLinkedInProvider` remain for tests.

## Alternatives

1. **SendGrid or AWS SES.** Rejected: while simpler to provision, they do not provide integrated reply ingestion, delivery status, and tenant directory access in the same API surface.
2. **Generic SMTP.** Rejected: lacks structured delivery/reply tracking and requires separate infrastructure for reply ingestion.
3. **Multiple providers in Phase 14.** Rejected: increases operational and testing scope before a single channel is proven.

## Rationale

Microsoft Graph aligns with the Microsoft ecosystem, provides send APIs, read/delivery status, webhook subscriptions for replies, and shared identity with Entra ID. A single provider reduces integration risk and validates the abstraction before adding more.

## Consequences

- A `GraphEmailProvider` adapter must be built.
- Entra ID application registration, token refresh, and least-privilege scopes are required.
- Webhook/polling infrastructure for reply ingestion is Graph-specific but abstracted behind `IReplyIngress`.
- Test doubles remain available for deterministic unit and CI tests.
