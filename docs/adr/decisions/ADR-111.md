# ADR-111: Conversation & Response Bounded Context Boundary

- **ADR ID:** ADR-111
- **Status:** Proposed
- **Group:** Conversation / Outreach
- **Date:** 2026-08-12
- **Decision Owners:** Architecture Review Board, CTO

## Context

Phase 12 completed the outbound execution kernel. The next capability needed is inbound reply handling: prospect responses must be ingested, interpreted, and turned into next-best actions without scattering the logic across outreach or mission orchestration.

## Decision

1. Create a new bounded context and package, `@projectx/conversation`, responsible for:
   - `Conversation` aggregate lifecycle.
   - Reply ingestion and idempotency.
   - Intent classification and next-best-action policy.
   - Lead re-qualification based on conversation outcome.
2. Keep `packages/outreach` focused on campaign/sequence/execution state; it emits reply-triggering events but does not own reply interpretation.
3. Keep `packages/mission-orchestrator` focused on mission lifecycle; it may reference conversation outcomes as mission results but does not own conversation state.
4. `packages/conversation` depends on `domain`, `shared`, `infrastructure`, `ai-runtime`, `outreach`, and `mission-orchestrator` only for wiring at the application/worker level.

## Alternatives

1. Extend `packages/outreach` with reply handling. Rejected: would couple multi-channel conversation logic to outbound channel execution.
2. Build reply handling inside `packages/mission-orchestrator`. Rejected: would overload the orchestrator with domain semantics and complicate future extraction.

## Rationale

A dedicated bounded context isolates reply interpretation, keeps aggregates small, and makes future extraction to an independent conversation service straightforward.

## Consequences

- New package and repository interfaces must be maintained.
- Temporal workflows/activities will bridge outbound sends and inbound replies while domain state remains in the aggregates.
