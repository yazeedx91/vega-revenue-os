# ADR-121: Inbound Email Ingestion Architecture

- **ADR ID:** ADR-121
- **Status:** Proposed
- **Group:** Conversation / Integration
- **Date:** 2026-08-13
- **Decision Owners:** Architecture Review Board, CTO

## Context

Phase 13 defined the `IReplyIngress` port and `StubReplyIngress` (`packages/conversation/src/infrastructure/stub-reply-ingress.ts`) for deterministic reply handling. Phase 14 needs a real mechanism to ingest replies from Microsoft Graph/Exchange Online.

## Decision

1. Primary ingestion mechanism: **Microsoft Graph webhook subscription** for the authenticated mailbox.
2. Fallback mechanism: **Microsoft Graph delta query / polling** for tenants or environments where webhooks are not feasible.
3. Normalize all inbound Graph payloads into the existing `ReplyIngressEvent` contract inside the adapter, not in the domain or application service.
4. Verify webhook signatures using Microsoft Graph certificate chain before normalization.
5. Deduplicate inbound notifications by `providerMessageId` + `Message-Id` header using the idempotency store.

## Alternatives

1. **IMAP polling only.** Rejected: Graph webhooks provide lower latency and richer metadata; IMAP is a separate credential model.
2. **Custom email receiving service.** Rejected: adds operational infrastructure; Graph already handles receive, storage, and notification.
3. **Pull replies from the send activity.** Rejected: violates the activity/workflow boundary and couples send to reply detection.

## Rationale

Graph webhooks give near-real-time reply detection with official SDK support. A normalized `ReplyIngressEvent` keeps the conversation bounded context provider-agnostic. Deduplication and signature verification prevent duplicate processing and spoofing.

## Consequences

- A `GraphWebhookIngressAdapter` and optional `GraphPollingIngressAdapter` must be built behind `IReplyIngress`.
- `apps/api` needs a secured webhook ingress endpoint.
- Webhook lifecycle management (subscription creation/renewal) is required.
- Signature verification failures are security events and must be alerted.
