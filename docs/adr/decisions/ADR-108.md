# ADR-108: Outreach Provider Port Abstraction

- **ADR ID:** ADR-108
- **Status:** Proposed
- **Group:** AI / Outreach
- **Date:** 2026-08-12
- **Decision Owners:** Architecture Review Board, CTO

## Context

Phase 12 will not integrate live email, LinkedIn, or calendar providers, but the architecture must support them in future phases without changing outreach business logic.

## Decision

1. Define a base port `IOutreachProvider` in `packages/outreach` with:
   - `providerId`
   - `channel`
   - `send(ctx, request)` returning a structured `ProviderSendResult`
   - `checkHealth(ctx)` for readiness checks
2. Define channel-specific sub-ports:
   - `IEmailProvider`
   - `ILinkedInProvider`
   - `ICalendarProvider`
3. Define `IOutreachProviderRegistry` to select a provider by tenant, channel, and configuration.
4. Implement only deterministic stub adapters in Phase 12:
   - `StubEmailProvider`
   - `StubLinkedInProvider`
   - `StubCalendarProvider`
5. Provider contracts must include:
   - Idempotency key
   - Correlation ID
   - Tenant context
   - Provider message ID on success
   - Retry classification (`RETRYABLE`, `NON_RETRYABLE`, `RATE_LIMITED`)
   - Rate-limit reset timing
   - Cost tracking

## Alternatives

1. Integrate a real email provider behind a feature flag. Rejected: Phase 12 explicitly forbids live external communication.
2. Put provider logic directly in the execution service. Rejected: no ability to swap or mock providers, and no clean rate-limit boundary.

## Rationale

A stable port with stub adapters lets the team validate the full send flow, idempotency, retry, and rate-limit behavior before live credentials are available.

## Consequences

- New providers only need an adapter implementing `IOutreachProvider`.
- The execution engine remains provider-agnostic.

## Risks

- Stub behavior may not cover all real provider edge cases (e.g., partial delivery, bounces). Future adapters must handle these explicitly.

## Security Impact

No credentials or secrets are stored or transmitted in Phase 12.

## Performance Impact

Stub calls are in-memory and fast; real adapters will add network latency.

## Scalability Impact

Provider registry supports per-tenant selection at scale.

## Cost Impact

None in Phase 12.

## Operational Impact

Operators can enable/disable providers per tenant through configuration.

## AI Impact

Agents do not need to know which provider delivers a message.

## Reversibility

High. New providers are additive.
