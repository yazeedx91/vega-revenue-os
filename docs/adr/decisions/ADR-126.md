# ADR-126: Centralized Workflow Identity

- **ADR ID:** ADR-126
- **Status:** Accepted
- **Group:** Workflow / Temporal Integration
- **Date:** 2026-08-17
- **Decision Owners:** Architecture Review Board, CTO

## Context

The codebase had two uncoordinated ways of deriving a Temporal workflow ID: `WorkflowIdFactory.forOutreachSequence()` in `packages/outreach` (used by the inbound reply-signal path) and an inline concatenation `mission:${tenantId}:${missionId}` in `packages/mission-orchestrator/src/application/approval-application.service.ts`. The latter also only ever signaled the mission workflow, never the outreach-sequence workflow that actually executes the send.

This duplication made the system fragile: a change in one convention would silently break signal routing, approval resume for outbound email had no complete code path, and cross-tenant workflow addressing was not centrally reviewed.

## Decision

1. Promote `WorkflowIdFactory` to a neutral shared home at `packages/shared/src/workflow/workflow-id-factory.ts`. It remains pure string formatting with zero business/domain logic.
2. The factory exposes two canonical constructors:
   - `forOutreachSequence(tenantId, sequenceId)` → `outreach-sequence-v1-{tenantId}-{sequenceId}`
   - `forMission(tenantId, missionId)` → `mission-v1-{tenantId}-{missionId}`
3. All call sites that derive or compare a workflow ID must use `WorkflowIdFactory`. Inline concatenation is prohibited.
4. `packages/outreach` re-exports the factory for backward compatibility with the existing inbound reply call site.

## Alternatives

1. **Keep the factory in `packages/outreach` and add a `forMission` method.** Rejected: it forces `mission-orchestrator` to depend on `outreach` for a neutral concern, creating the wrong package boundary.
2. **Pass workflow IDs around as opaque strings and let each caller decide.** Rejected: reproduces the duplication that caused the bug; signal routing cannot be verified centrally.

## Rationale

A single, versioned, tenant-scoped naming convention makes workflow addressing deterministic, auditable, and recoverable. Putting it in `packages/shared` preserves the existing package layering while allowing every workflow-start and signal-dispatch path to produce the same ID for the same logical target.

## Consequences

- `ApprovalApplicationService.signalWorkflow()` must derive its target workflow ID from the factory, branching between mission and outreach-sequence targets.
- Any future workflow type must register its constructor in `WorkflowIdFactory` and use the same tenant-safe, versioned format.
- `packages/outreach` keeps a re-export; no breaking change to the inbound Graph dispatcher.

## Security Impact

Centralized, tenant-scoped IDs reduce the risk of a signal being routed to the wrong tenant's workflow when a caller accidentally omits the tenant qualifier.

## Risks

- If the format is later changed, all in-flight workflow IDs become orphaned. Mitigation: the `v1` namespace and an explicit ADR-driven migration path.
